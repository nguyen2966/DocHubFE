Fix inconsistent avatar marker coordinate source after creating comments.

Current bug:
On a completely new document, each created comment only renders one avatar marker. However, some markers behave correctly as page-bound markup, while some markers behave incorrectly as viewport-fixed markup when scrolling.

This means the issue is not duplicate rendering.

Root cause to investigate:
Some marker instances are probably created from PDF page coordinates, while others are created from viewport/client/overlay coordinates.

Correct behavior:
Every persisted avatar marker must use the same source of truth:

* pageNumber
* pageRect in PDF page coordinates

Never use viewport/client/overlay coordinates as the persisted marker source.

Important distinction:

* page coordinate / pageRect: used to render avatar marker.
* clientPosition / DOMRect: used only to position CommentThreadPopover.
* overlayRect: derived render output only, never source of truth.

Scope:

* FE only.
* Do not modify BE.
* Do not change API payload shape.
* Do not change comment data model.
* Keep locked zoom behavior.
* Keep React page-bound avatar markup.
* Do not use Apryse StampAnnotation for avatar markers.
* Do not reintroduce viewport-fixed avatar markers.
* Keep native Apryse highlight rendering.

Files to inspect/update:

* src/features/documents/components/details-page/AprysePdfViewer.tsx
* src/features/comments/components/CommentAnnotationOverlayLayer.tsx
* src/features/comments/components/CommentAnchorMarker.tsx
* src/pages/document-details/DocumentDetailPage.tsx
* any file involved in createPendingCommentAnchor / submit comment / pending anchor state

Main requirement:
There must be exactly one coordinate pipeline for persisted avatar markers:

PDF page coordinate/pageRect
→ project to overlayRect for current viewer scroll/layout
→ render React marker absolute inside viewer overlay

There must be no path where persisted marker source is:

* clientPosition
* getBoundingClientRect
* overlayPosition
* pageToWindow output directly
* mouse event x/y
* SelectionCommentAction position
* popover position

2. Enforce marker model with explicit types

Use types like:

type PagePoint = {
pageNumber: number
x: number
y: number
}

type PageRect = {
x: number
y: number
width: number
height: number
}

type PageBoundAvatarMarker = {
annotationId: string
thread: CommentThread
pageNumber: number
pageRect: PageRect
}

type ProjectedAvatarMarker = PageBoundAvatarMarker & {
overlayRect: {
left: number
top: number
width: number
height: number
}
}

Rules:

* PageBoundAvatarMarker is source.
* ProjectedAvatarMarker is derived render state.
* Never create PageBoundAvatarMarker from clientPosition or overlayRect.
* Never save overlayRect back into pageRect.

3. Fix comment creation flow

When user selects text and creates a comment:

createPendingCommentAnchor should produce:

* pageNumber
* position in PDF page coordinates
* xfdf if visualState is highlight
* apryseAnnotationId
* visualState

The position must be derived from Apryse selection/page geometry, not from the Add Comment button position or mouse/client coordinates.

If current code has something like:

* selectionActionPosition
* clientPosition
* normalizedClientPosition
* overlay position

Do not use it for annotation.position.

It can only be used for:

* placing temporary Add Comment button
* opening CommentComposer
* opening CommentThreadPopover

4. Build avatar marker only from thread annotation data or imported highlight geometry

For each thread:

const visualState =
annotation.visualState ?? (annotation.xfdf ? "highlight" : "point")

If visualState === "highlight" and imported highlight annotation exists:

* use imported highlight geometry as primary source:

pageNumber = importedHighlight.PageNumber
anchorX = importedHighlight.X + importedHighlight.Width
anchorY = importedHighlight.Y + importedHighlight.Height / 2

If imported highlight geometry is unavailable:

* fallback only to annotation.position if it is known to be PDF page coordinate.
* never fallback to clientPosition.

If visualState === "point":

* use annotation.position and annotation.pageNumber.
* skip stale xfdf.

Then create pageRect from page coordinate constants:

pageRect = {
x: anchorX + AVATAR_MARKER_GAP_PAGE,
y: anchorY - AVATAR_MARKER_HEIGHT_PAGE / 2,
width: AVATAR_MARKER_WIDTH_PAGE,
height: AVATAR_MARKER_HEIGHT_PAGE,
}

5. Add coordinate invariant guards

Add development-only warnings when marker source looks suspicious.

Example checks:

* pageNumber must be >= 1
* pageRect.x/y should be reasonable for page size
* pageRect.width/height should be small page units, not huge viewport pixels
* pageRect should not equal overlay/client coordinates

If possible, get page dimensions from document:

* page width / height
* warn if x/y are outside a reasonable page range

Example warning:

console.warn('[DocHub marker] Invalid pageRect source; refusing to render viewport-based marker', {
annotationId,
pageNumber,
pageRect,
pageSize,
source,
})

If pageRect is invalid, do not render marker rather than rendering a viewport-fixed marker.

6. Project pageRect to overlayRect in exactly one helper

Use one helper only:

pageRectToOverlayRect({
pageNumber,
rect,
})

It should:

* take PDF page rect.
* use Apryse pageToWindow for top-left and bottom-right.
* convert to client coordinate if needed.
* subtract overlayRoot.getBoundingClientRect().
* return overlay-relative rect.

This helper must be the only place where page coordinates become screen/overlay coordinates.

7. Do not persist or reuse overlayRect

On scroll/page change:

* recompute overlayRect from original pageRect.
* do not mutate pageRect.
* do not use previous overlayRect as source.

On commentThreads refetch:

* rebuild PageBoundAvatarMarker from annotation/page geometry.
* project again.

8. Pending/new comment marker behavior

After submitting a new comment:

* clear pending composer state.
* clear temporary selection UI.
* do not render final avatar marker from pending client coordinates.
* final marker should appear from:

  * returned/refetched thread annotation data
  * or imported highlight geometry tagged with the Mongo annotation id

If there is an optimistic marker:

* it must also use pageRect derived from PDF page coordinate.
* otherwise disable optimistic persisted marker and wait for refetch.

9. CommentAnchorMarker must not be fixed

Verify persisted marker component:

* no position: fixed
* no className fixed
* no viewport left/top source
* no clientPosition prop

It should receive only overlayRect:

style={{
position: 'absolute',
left: overlayRect.left,
top: overlayRect.top,
width: overlayRect.width,
height: overlayRect.height,
}}

10. CommentThreadPopover can still use clientPosition

Popover is allowed to be viewport fixed.

When user clicks marker:

* use marker DOMRect to compute clientPosition:
  rect.right
  rect.top + rect.height / 2

This clientPosition is only for popover placement.
Do not feed it back into avatar marker state.
